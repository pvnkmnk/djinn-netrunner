## Findings

### 1. `/rest/license.view` was an endpoint no client could reach

The License handler was registered as `/rest/license.view`; the spec's name
is `getLicense`. A conformant client asking for the licence got a 404 while
the handler worked fine, and nothing in the suite could see it:
`subsonic.spec.ts` has a case called *License endpoint works* which passed
because it called the wrong URL, and `TestSubsonic_License` drove the handler
directly. Route existence, a handler test and a green browser spec all agreed
while the feature was unreachable to the clients that need it.

Fixed: `/rest/getLicense.view` is the spec name and `/rest/license.view` is
kept as an alias, so nothing breaks for a client that learned the old one.
The guard below fails if either half of that pair disappears.

### 2. `/rest/stream.view` has no automated test

`SubsonicHandler.Stream` (`backend/internal/api/subsonic.go:871`) is the
endpoint every client actually uses to listen to music. One check drives it —
`scripts/smoke.sh:486-492`, which fetches a track and fails unless more than
1,000 bytes come back. That is a happy path with no assertion about ranges,
content type, authorization or error shape, it needs a running stack, and
**no workflow invokes `smoke.sh`**, so nothing runs it on a change. An earlier
draft of this document called the endpoint untested; it is not, and the
distinction is the point: the check exists somewhere a CI failure cannot
reach it.

There are nine passing tests named `TestStreamTrack_*` in
`backend/internal/api/stream_test.go` covering BOLA, admin access, `200`,
`206` range and the error paths. They test a **different handler** —
`LibraryHandler.StreamTrack`, registered at `/tracks/:id/stream` — so a name
match between `Stream` and `StreamTrack` reads as coverage that is not there.
Streaming is the endpoint whose failure a user notices first, so it is the
one gap here that matters more than its size.

### 3. Discovery is the base-API hole that hides every other one

`getOpenSubsonicExtensions` is base API (tags `System`, `Addition`, no
extension requirement) and unimplemented. A client cannot ask which of the
11 extensions this server supports, so every extension below is
invisible rather than absent. `tokenInfo` is extension-gated
(`apiKeyAuthentication`), so it is correctly counted as an NR05 gap rather
than a base-API one.

### 4. Eleven endpoints had no ticket behind them (resolved 2026-10-08)

Podcast (8), chat (2) and `jukeboxControl` (1) appear in the spec but in
none of NR01-NR25, so the wave order could not reach them and no wave
could clear them. That was a scope decision rather than an
implementation gap, and it has been made: every one now has an owner.

| feature | endpoints | owner |
|---|---|---|
| podcast | 8 | NR26 (DJI-620) |
| chat | 2 | NR27 (DJI-621) |
| jukebox | 1 | NR28 (DJI-622) |

The `getPodcastEpisode` extension in the ledger is owned by NR26 as well.
Ownership is not a claim that any of these is implemented: every one is
still a gap row, and a ticket may legitimately close by recording its
endpoints as deliberately unsupported, with the reason.

## Guard

`backend/cmd/server/opensubsonic_coverage_test.go` reads the `impl` rows
above and compares them with `app.GetRoutes()` under
`cfg.Subsonic.Enabled = true`. It fails if this document claims an endpoint
that is not registered, or omits one that is — so the coverage number above
cannot rot into a claim. It also asserts both `getLicense.view` and the
`license.view` alias are registered.

The guard reads the first column of the status position, so it is unaffected
by the extra `spec tag` column; the row regexp pins the column count.
